## 1. 개요

### 목적

이 문서는 TodoList 애플리케이션의 핵심 사용자 시나리오를 정의한다. 두 가지 주요 페르소나(김철수 개발자, 박소영 가정주부)를 중심으로 실제 사용 흐름을 기술하여, 기능 요구사항의 올바른 이해와 테스트 케이스 도출을 지원한다.

### 대상 독자

- 프로덕트 개발팀 (개발자, 테스터, 기획자)
- 스테이크홀더
- QA 엔지니어

### 문서 구조

1. **개요**: 목적 및 대상 독자
2. **시나리오 목록**: 페르소나별, 유스케이스별 상세 시나리오
3. **커버리지 매트릭스**: 시나리오와 유스케이스 매핑 표
4. **변경 이력**: 버전 관리

## 2. 시나리오 목록

### SC-01: 회원가입 - 정상 흐름 (페르소나 A)

**시나리오 ID:** SC-01
**시나리오 제목:** 개발자 김철수의 회원가입

**페르소나:** 김철수 (27세, 스타트업 개발자)

**관련 UC:** UC-01
**관련 BR:** BR-02, BR-03, BR-10, BR-11

**사전 조건:**
- 사용자가 애플리케이션에 접속했으나 인증되지 않은 상태
- 회원가입 화면이 표시된 상태

**정상 흐름:**
1. 사용자가 회원가입 버튼 클릭
2. 회원가입 폼이 표시됨 (이메일, 비밀번호 입력 필드)
3. 사용자가 유효한 이메일 주소 입력: `chulsu.kim@startup.com`
4. 사용자가 복잡도 높은 비밀번호 입력: `SecurePass123!`
5. 사용자가 비밀번호 확인 입력: `SecurePass123!`
6. 사용자가 회원가입 버튼 클릭
7. 시스템이 입력 값 검증 수행:
   - 이메일 형식 확인 ✓
   - 비밀번호 길이 8자 이상 확인 ✓
   - 비밀번호에 영문(a-z, A-Z), 숫자(0-9), 특수문자(!@#$%^&*) 포함 여부 확인 ✓
   - 두 비밀번호 일치 여부 확인 ✓
8. 시스템이 이메일 중복 여부 확인
9. 새로운 사용자 레코드 생성 (bcrypt로 해시된 비밀번호 저장)
10. 시스템이 성공 메시지 표시: "회원가입이 완료되었습니다"
11. 사용자가 로그인 화면으로 리다이렉트됨

**사후 조건:**
- 새로운 사용자가 데이터베이스에 생성됨
- 사용자 이메일이 시스템에 등록됨
- 사용자가 로그인 화면에 위치
- 사용자는 아직 인증되지 않은 상태

### SC-02: 회원가입 - 중복 이메일 실패 케이스 (페르소나 A)

**시나리오 ID:** SC-02
**시나리오 제목:** 이미 가입된 이메일로 회원가입 시도

**페르소나:** 김철수 (27세, 스타트업 개발자)

**관련 UC:** UC-01
**관련 BR:** BR-02, BR-10, BR-11

**사전 조건:**
- 이메일 `chulsu.kim@startup.com`이 이미 시스템에 등록되어 있음
- 사용자가 회원가입 폼을 입력 중

**정상 흐름:**
1. 사용자가 기존 사용자와 동일한 이메일 입력: `chulsu.kim@startup.com`
2. 사용자가 유효한 비밀번호 입력: `NewPass456!`
3. 사용자가 회원가입 버튼 클릭
4. 시스템이 입력 값 검증 수행 (모두 통과)
5. 시스템이 이메일 중복 확인
6. 데이터베이스에서 동일 이메일 발견
7. 시스템이 에러 메시지 표시: "이미 가입된 이메일입니다"
8. 회원가입 폼이 유지됨 (입력 값 일부 보존, 비밀번호는 초기화)

**예외 흐름:**
- 사용자가 "로그인" 링크 클릭 → 로그인 페이지로 이동

**사후 조건:**
- 새로운 사용자 레코드가 생성되지 않음
- 사용자가 여전히 회원가입 폼에 위치
- 에러 메시지가 표시된 상태

### SC-03: 회원가입 - 약한 비밀번호 실패 케이스 (페르소나 B)

**시나리오 ID:** SC-03
**시나리오 제목:** 비밀번호 복잡도 부족으로 회원가입 실패

**페르소나:** 박소영 (34세, 가정주부+쇼핑몰 운영자)

**관련 UC:** UC-01
**관련 BR:** BR-11

**사전 조건:**
- 사용자가 회원가입 폼에 이메일 입력함: `soyoung.park@shoppingmall.com`
- 비밀번호 입력 필드가 활성 상태

**정상 흐름:**
1. 사용자가 복잡도가 낮은 비밀번호 입력: `password123` (특수문자 없음)
2. 사용자가 확인 비밀번호 입력: `password123`
3. 사용자가 회원가입 버튼 클릭
4. 시스템이 비밀번호 복잡도 검증
5. 검증 실패: 특수문자 누락
6. 시스템이 에러 메시지 표시: "비밀번호는 영문, 숫자, 특수문자를 포함해야 합니다"
7. 비밀번호 입력 필드가 강조 표시됨 (시각적 피드백)

**대안 흐름:**
- 사용자가 비밀번호 수정: `Password123!` → 다시 회원가입 시도

**사후 조건:**
- 회원가입이 진행되지 않음
- 사용자가 여전히 회원가입 폼에 위치
- 에러 메시지와 함께 비밀번호 입력 필드 강조

### SC-04: 로그인 - 정상 흐름 (페르소나 A)

**시나리오 ID:** SC-04
**시나리오 제목:** 개발자 김철수의 로그인

**페르소나:** 김철수 (27세, 스타트업 개발자)

**관련 UC:** UC-02
**관련 BR:** BR-01

**사전 조건:**
- 사용자가 로그인 화면에 위치
- 사용자 `chulsu.kim@startup.com`이 이미 시스템에 가입되어 있음
- 사용자가 인증되지 않은 상태

**정상 흐름:**
1. 사용자가 로그인 폼 입력 필드에 이메일 입력: `chulsu.kim@startup.com`
2. 사용자가 비밀번호 입력 필드에 비밀번호 입력: `SecurePass123!`
3. 사용자가 "로그인" 버튼 클릭
4. 시스템이 입력 값 검증 (형식 확인)
5. 시스템이 데이터베이스에서 이메일로 사용자 조회
6. 사용자 레코드가 발견됨
7. 시스템이 입력된 비밀번호와 저장된 해시 비교
8. 비밀번호 일치 확인
9. 시스템이 JWT 토큰 생성 (HS-512 알고리즘 사용)
10. 시스템이 토큰을 클라이언트에 반환 (HttpOnly 쿠키 또는 로컬 스토리지)
11. 사용자가 대시보드로 리다이렉트됨
12. 대시보드가 인증된 사용자 정보와 함께 표시됨 (이메일, 가입일)

**사후 조건:**
- 사용자가 로그인한 상태 (JWT 토큰 보유)
- 대시보드가 표시됨
- 모든 기능(카테고리, 할일 관리 등)에 접근 가능
- 사용자가 본인이 소유한 데이터만 조회 가능

### SC-06: 카테고리 생성 - 정상 흐름 (페르소나 A)

**시나리오 ID:** SC-06
**시나리오 제목:** 개발자가 업무/개인 카테고리 생성

**페르소나:** 김철수 (27세, 스타트업 개발자)

**관련 UC:** UC-04
**관련 BR:** BR-04, BR-09

**사전 조건:**
- 사용자가 로그인한 상태
- 사용자가 대시보드에 위치
- 사용자가 아직 카테고리를 생성하지 않음

**정상 흐름:**
1. 사용자가 대시보드 좌측 메뉴에서 "카테고리 관리" 버튼 클릭
2. 카테고리 관리 모달 또는 페이지가 열림
3. 사용자가 "새 카테고리" 버튼 클릭
4. 카테고리 생성 폼이 표시됨
5. 사용자가 카테고리 이름 입력: "업무"
6. 사용자가 "저장" 버튼 클릭
7. 시스템이 입력 값 검증 (이름 필수, 공백만 불가)
8. 시스템이 동일 사용자 내 카테고리 이름 중복 확인
9. 중복 없음 확인
10. 시스템이 새로운 카테고리 레코드 생성 (userId와 함께 저장)
11. 시스템이 성공 메시지 표시: "카테고리가 생성되었습니다"
12. 카테고리 목록이 업데이트되어 "업무" 카테고리가 표시됨

**대안 흐름:**
1. 사용자가 두 번째 카테고리 생성 시도: "개인"
2. 동일 절차 수행
3. 시스템이 "개인" 카테고리 추가 생성

**사후 조건:**
- 사용자가 소유한 카테고리가 생성됨
- 카테고리 목록에 새 카테고리가 표시됨
- 사용자만 자신의 카테고리를 조회·수정·삭제 가능

### SC-08: 할일 생성 - 정상 흐름 (페르소나 B)

**시나리오 ID:** SC-08
**시나리오 제목:** 가정주부가 장보기 할일 생성

**페르소나:** 박소영 (34세, 가정주부+쇼핑몰 운영자)

**관련 UC:** UC-05
**관련 BR:** BR-06, BR-08, BR-09

**사전 조건:**
- 사용자가 로그인한 상태
- 사용자가 "가사" 카테고리를 이미 생성한 상태
- 사용자가 대시보드에서 "할일 추가" 버튼을 볼 수 있음

**정상 흐름:**
1. 사용자가 "할일 추가" 버튼 클릭
2. 할일 생성 폼이 표시됨 (제목*, 설명, 카테고리, 종료일 필드)
3. 사용자가 제목 입력: "주간 장보기"
4. 사용자가 설명 입력: "우유, 계란, 채소 구입" (선택)
5. 사용자가 카테고리 선택: "가사"
6. 사용자가 종료일시 설정: "2026-05-02 18:00" (선택)
7. 사용자가 "저장" 버튼 클릭
8. 시스템이 입력 값 검증:
   - 제목 필수 확인 ✓
   - 제목 길이 확인 (예: 1~255자) ✓
9. 시스템이 카테고리 소유권 확인 (사용자가 선택한 카테고리 소유 여부)
10. 소유권 확인 ✓
11. 시스템이 종료일시 형식 검증 (있을 경우)
12. 형식 유효 ✓
13. 시스템이 새로운 할일 레코드 생성:
    - userId: 현재 사용자 ID
    - title: "주간 장보기"
    - description: "우유, 계란, 채소 구입"
    - categoryId: "가사" 카테고리 ID
    - dueDate: "2026-05-02 18:00"
    - status: "PENDING" (조회 시점에 현재 시각과 비교하여 판별)
14. 시스템이 성공 메시지 표시: "할일이 생성되었습니다"
15. 할일 목록이 업데이트되어 새로운 할일이 표시됨

3. 시스템이 요청 거부:
   - HTTP 상태 코드: 403 Forbidden
   - 응답 바디: { "error": "접근 권한이 없습니다" }
4. 프론트엔드가 403 에러 처리
5. 사용자에게 에러 메시지 표시: "접근할 수 없는 할일입니다"

**정상 흐름 (UI 레벨):**
1. 사용자 A가 할일 목록에서 조회
2. 시스템이 "SELECT * FROM tasks WHERE userId = user-001" 쿼리 실행
3. 사용자 B의 할일은 쿼리 결과에 포함되지 않음
4. 사용자 A의 할일만 목록에 표시됨

**예외 흐름:**
- 사용자가 인증 없이 API 요청:
  - JWT 토큰 없음
  - 시스템이 401 Unauthorized 반환
  - 로그인 페이지로 리다이렉트

**사후 조건:**
- 타인의 데이터 접근 차단
- 403 에러 반환
- 사용자는 본인의 데이터만 조회 가능

### SC-16: 로그아웃 (페르소나 B)

**시나리오 ID:** SC-16
**시나리오 제목:** 가정주부의 로그아웃

**페르소나:** 박소영 (34세, 가정주부+쇼핑몰 운영자)

**관련 UC:** UC-03
**관련 BR:** BR-01

**사전 조건:**
- 사용자가 로그인한 상태
- 사용자가 대시보드에 위치
- JWT 토큰이 클라이언트에 저장되어 있음

**정상 흐름:**
1. 사용자가 상단 메뉴의 프로필 아이콘 또는 "로그아웃" 버튼 클릭
2. 시스템이 로그아웃 확인 (선택):
   - 즉시 로그아웃하거나 확인 모달 표시
3. 사용자가 로그아웃 확인
4. 클라이언트가 저장된 JWT 토큰 제거:
   - 로컬 스토리지에서 토큰 삭제 또는
   - HttpOnly 쿠키 무효화
5. 프론트엔드가 전역 상태 초기화 (Zustand 스토어 리셋)
6. 시스템이 로그인 페이지로 리다이렉트
7. 로그인 페이지 표시

**대안 흐름:**
- 사용자가 로그아웃 중 네트워크 오류 발생:
  - 클라이언트가 로컬 토큰 여전히 제거
  - 사용자가 로그인 페이지로 이동
  - 토큰 없이는 API 요청 불가능

**예외 흐름:**
- 사용자가 토큰 만료 상태에서 로그아웃 시도:
  - 클라이언트가 토큰 제거
  - 로그인 페이지로 리다이렉트

**사후 조건:**
- 사용자가 로그아웃한 상태
- JWT 토큰이 클라이언트에서 제거됨
- 모든 API 요청에 401 인증 오류 발생
- 사용자가 로그인 페이지에 위치
- 사용자 정보 및 데이터는 서버에 유지됨 (다음 로그인 시 재접근 가능)
